電球とスイッチで学ぶ

02 / 使う理由と、学ぶ目的

なぜSOLIDを使うのか？

機器の追加で、動いている他の処理まで直さないためです。

この資料で伝えたいこと

「変更したい所だけを変えられる設計」を選ぶ。

03 / まず、何をするコードか

スイッチに合わせて、電球を点ける。

スイッチの状態に、電球の明かりを合わせます。

main＝プログラムの入口Kotlin
fun main() {
    val bulb = B9000()
    val switch = S9000()
    while (true) {
        if (switch.isOn()) {
            bulb.turnOn()
        } else {
            bulb.turnOff()
        }
    }
}

04 / D · 依存関係逆転の原則

機種名ではなく、必要な操作でつなぐ。

制御役と機器の間に、共通の操作の約束を置きます。

一言で表すなら特定の製品ではなく、できることを頼りにする。
interface＝操作の約束Kotlin
interface Bulb {
    fun turnOn()
    fun turnOff()
}

interface Switch {
    fun isOn(): Boolean
}

05 / D · 実際の製品とのつなぎ方

実際の電球は、制御の外で選ぶ。

入口mainで製品を選び、制御役へ渡します。

入口のmainで、使う製品を選んで渡すKotlin
fun main() {
    val app = SmartHomeApp(B9000(), S9000())
    while (true) {
        app.runOnce()
    }
}

選ぶ場所と、判断する場所を分ける。

06 / S · 単一責任の原則

電源の操作と、指示を出す判断を分ける。

読む・判断する・操作する。変わる理由で分けます。

一言で表すなら違う理由で変わる処理を、別々に持つ。
runは判断だけを担当するKotlin
fun run(thing: OnOffThing, switch: Switch) {
    if (switch.isOn()) {
        thing.turnOn()
    } else {
        thing.turnOff()
    }
}

コード出典：Sの解答ブランチ

07 / S · 変更する理由を見分ける

スイッチの変更は、スイッチ側に閉じ込める。

読む方法の変更なら、判断や電球の操作は変えません。

S9000＝スイッチの読み取り役Kotlin
class S9000: Switch {
    override fun isOn(): Boolean {
        return true
    }
}

異なる変更理由を、一つの処理に混ぜない。

コード出典：Sの解答ブランチ

08 / O · 開放閉鎖の原則

テレビを増やしても、制御の判断は変えない。

追加するのは機器。共通のオン・オフ判断は残します。

一言で表すなら新しい機能は追加し、安定した処理は書き換えない。
run＝機器が増えても変えない判断Kotlin
fun run(thing: OnOffThing, switch: Switch) {
    if (switch.isOn()) {
        thing.turnOn()
    } else {
        thing.turnOff()
    }
}

コード出典：Oの解答ブランチ

09 / O · 増やす部分と、変えない部分

テレビにも、同じオン・オフ操作を用意する。

テレビ用の操作を追加し、既存のrunから使います。

TV9000＝追加するテレビKotlin
class TV9000 : OnOffThing {
    var isOn = false

    override fun turnOn() {
        isOn = true
    }

    override fun turnOff() {
        isOn = false
    }
}

増やすのは機器。共通の判断はそのまま。

10 / L · リスコフの置換原則

電球を交換しても、操作の結果をそろえる。

どの電球でも、点けたらON・消したらOFFです。

一言で表すなら入れ替えても、使う側との約束を守る。
Bulb＝電球の型Kotlin
interface Bulb {
    val isOn: Boolean
    fun turnOn()
    fun turnOff()
}

コードと動作の約束の出典：Lの解答ブランチ

11 / L · 交換後も同じ結果になるか確かめる

LED電球でも、同じ確認が通る。

同じON指示なら、電球を替えても点灯します。

LedBulb＝LED電球のテストKotlin
    @Test
    fun `LedBulbはスイッチがオンなら点灯する`() {
        val bulb: Bulb = LedBulb()

        run(bulb, onSwitch)

        assertEquals(true, bulb.isOn)
    }

差し替え先でも、操作の結果を守る。

12 / I · インターフェース分離の原則

電球の操作と、スイッチの操作を分ける。

電源操作と状態確認を、別々の約束にします。

一言で表すなら使わない操作への依存を、押し付けない。
電球とスイッチを分けた型Kotlin
interface Bulb {
    fun turnOn()
    fun turnOff()
}

interface Switch {
    fun isOn(): Boolean
}

コード出典：Iの解答ブランチ

13 / I · 機器にも不要な操作を持たせない

それぞれの機器は、必要な操作だけを用意する。

電球は電源操作だけ。スイッチは状態確認だけ。

B9000＝電源操作だけを持つ電球Kotlin
class B9000 : Bulb {
    override fun turnOn() {
        println("turnOn")
    }

    override fun turnOff() {
        println("turnOff")
    }
}

使わない操作を、持ち込まない。

15 / 最後に、適用するための費用も考える

SOLIDにも、設計が重くなるデメリットがある。

分けすぎると、作る手間も読む負担も増えます。

必要な変更を楽にする分だけ使う。

変更が楽になる効果と、分ける負担を比べる。
